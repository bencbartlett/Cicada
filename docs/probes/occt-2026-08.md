### 00:58–01:10 — Q2: determinism across processes

Method: `occt-probe dump <dir>` builds the four probe shapes from
transcendental-free inputs (box 10×20×30 at the origin; rectangle 4×6
from four explicit points extruded 40 along Z; box − prism; loft between
a 10×20 rectangle at z=0 and a 6×12 rectangle at z=30), writes each with
`Shape::write_brep_bin` (BinTools) and `Shape::write_brep_text`
(BRepTools) BEFORE any tessellation, hashes the files, tessellates
(deflection 0.01), hashes positions+indices and normals separately, then
re-reads the BinTools file and re-writes it (round trip). Two separate
processes (`run1`, `run2`, fresh cwd, nothing cached on disk by OCCT),
compared line-by-line and with `cmp` on the raw files.

**Two binding defects surfaced before the question could be answered
honestly** (both now carried as probe patches and both required for
Item 3 WP-B):

1. **`write_brep_bin` was silently the text writer.** First run: the
   "BinTools" and "BRepTools" files were byte-identical (2,565 B) and
   both started with `DBRep_DrawableShape … CASCADE Topology V3`. Root
   cause (verified with `dumpbin /linkermember:1` on `rust-occt.lib`):
   the `bin_tools` and `b_rep_tools` cxx bridges both declare
   `fn write` / `fn read` in the root namespace with different
   `#[cxx_name]`s, but cxx mangles the *Rust* name —
   `cxxbridge1$199$write` / `$read` — so two archive members define the
   same symbols; the archive index points both at `b_rep_tools.rs.o`,
   `bin_tools.rs.o` has no unique symbol and is never pulled, and no
   toolchain warns (the same archive-member logic holds for GNU ld, so
   this is not Windows-specific). `Shape::write_brep_bin` /
   `read_brep_bin` in the shipped binding therefore read and write the
   ASCII format. Fix: `patches/0002-bin-tools-symbol-collision.diff`
   (4 lines: rename the bridge fns to `write_bin`/`read_bin`, update the
   two call sites in `shape.rs`). Worth an upstream issue; the fork
   carries it regardless.
2. **OCCT 7.8's path-taking `Write` overloads default to
   `theWithTriangles = TRUE`** (`BinTools.hxx` line 93 ff.: "This alias
   writes shape with triangulation data"; same for `BRepTools::Write`),
   and the binding passes only the path. Measured: writing the same
   shape again AFTER `mesh()` changes the bytes — box 4,494 → 6,931 B,
   extrude 2,303 → 4,347 B, difference 8,821 → 13,747 B, loft 4,790 →
   43,067 B (`identical_to_premesh=false` for all four). A `Solid`
   whose canonical bytes were taken after display tessellation would
   hash differently from the same solid serialized before it. The WP-B
   serializer must call the 5-argument overload with
   `theWithTriangles = false, theWithNormals = false` and a PINNED
   `BinTools_FormatVersion` (not `_CURRENT`, which moves with OCCT
   releases) — a ~6-line glue function in the fork, not an upstream
   question.

**Results with the real BinTools path (two processes):**

| Shape | BinTools V4 bytes | sha256 (prefix) | BRepTools text bytes | mesh verts / tris | identical across processes |
|---|---|---|---|---|---|
| box | 4,494 | `d83ce546…` | 2,565 | 24 / 12 | bin ✓ text ✓ after-mesh ✓ mesh ✓ normals ✓ |
| extrude | 2,303 | `b0265b60…` | 1,623 | 24 / 12 | bin ✓ text ✓ after-mesh ✓ mesh ✓ normals ✓ |
| difference | 8,821 | `d2d1784f…` | 5,237 | 48 / 32 | bin ✓ text ✓ after-mesh ✓ mesh ✓ normals ✓ |
| loft | 4,790 | `711eaf3d…` | 3,001 | 584 / 1,132 | bin ✓ text ✓ after-mesh ✓ mesh ✓ normals ✓ |

- `diff run1.txt run2.txt` is empty; `cmp` on all 12 files (4 shapes ×
  bin / brep / after_mesh.bin) reports identical. Full hashes are in the
  run logs (`C:\Users\benja\AppData\Local\cicada-occt\det\run{1,2}.txt`)
  and reproducible with the committed probe.
- **Round trip is byte-stable**: `BinTools::Read` → `BinTools::Write`
  reproduces the original bytes exactly for all four shapes — the
  format is a fixed point, so "canonical bytes = BinTools V4 of the
  shape" is well defined and re-hydrating from the store will not
  drift the hash.
- **Nothing run-dependent in either writer.** BinTools V4 header:
  `\nOpen CASCADE Topology V4, (c) Open Cascade\n` then `Locations`,
  `Curve2ds`, …; BRepTools: `DBRep_DrawableShape\n\nCASCADE Topology
  V3, (c) Open Cascade\n`. Format-version strings only — no date, no
  build id, no OCCT version. (The STEP writer, by contrast, DOES stamp
  `FILE_NAME(... '2026-08-20T…' ...)`; that is the "header timestamps
  normalized" line already in Item 3 WP-C.)
- The binary format is LARGER than the text format for these shapes
  (raw IEEE doubles vs shortest-decimal text of round numbers) — size
  is not an argument either way; hash the binary: it is exact and
  needs no float-printing policy.
- The `difference` result is a `TopoDS_Compound` holding one solid;
  the compound wrapper is part of the serialized bytes, so the `Solid`
  constructor must normalize (unwrap single-solid compounds, or refuse
  multi-solid results loudly) BEFORE hashing, or identical solids
  reached via different operations hash differently.

**What this does and does not decide.** On one machine / one compiler /
one OCCT build, OCCT's B-rep construction and serialization are
byte-deterministic for these inputs, so **`Solid` can hash its canonical
BinTools bytes** (blake3 at construction, the Merkle model unchanged)
rather than a geometric summary — exactly like the Manifold seam.
What remains open is cross-OS/cross-build identity (different libm,
different compiler flags in the three conda builds, FMA contraction):
the golden-hash CI job in Item 3 WP-A decides whether the golden hashes
are per-OS or universal. The fallback if they diverge is already in
docs/17 ("or the determinism policy the probe forced is recorded"):
per-platform golden files, not a summary hash.

### 01:10–01:20 — Q3: timings (release build)

`occt-probe bench <parts>`: `parts` independent parts, each at its own
X offset; per op, wall-clock over all parts then per part. One thread
(the binding exposes no `SetRunParallel`; OCCT's own parallelism is off
by default). Ryzen-class 24-thread desktop; numbers from the second of
two runs — the first run at each size agreed within 5 %.

| op (per part) | 1 part | 100 parts | 1,000 parts | per part @1,000 |
|---|---|---|---|---|
| `box` (`BRepPrimAPI_MakeBox`) | 0.113 ms | 2.64 ms | 23.5 ms | **0.024 ms** |
| `extrude` (4-pt wire → face → `MakePrism`) | 0.343 ms | 9.95 ms | 95.6 ms | **0.096 ms** |
| `difference` (`BRepAlgoAPI_Cut`, box − prism) | 3.69 ms | 288.5 ms | 2,850 ms | **2.85 ms** |
| `mesh(occt)` (`BRepMesh_IncrementalMesh`, deflection 0.01) | 0.99 ms | 85.7 ms | 850 ms | **0.85 ms** |
| `mesh(extract)` (binding's per-node FFI copy-out) | 0.025 ms | 1.30 ms | 13.4 ms | 0.013 ms |
| `tessellate` = mesh + extract | 1.02 ms | 87.0 ms | 864 ms | **0.86 ms** |
| `loft` (`ThruSections`, two rectangles, solid) | 1.20 ms | 82.5 ms | 839 ms | 0.84 ms |

- **Linear in parts** — no super-linear surprises from 1 to 1,000; the
  1-part numbers carry ~0.5 ms of first-call warm-up (allocator,
  page-ins), which is why per-part at 1 > per-part at 1,000.
- **A simple boolean costs ~3 ms**; a 1,000-part box-minus-prism
  pipeline is 2.85 s of booleans + 0.86 s of tessellation + 0.12 s of
  primitives ≈ **3.8 s single-threaded**. For scale, the wall corpus's
  1,200-part cold carve on the Manifold mesh tier is 6.5 s with the
  rayon fan-out (docs/15). OCCT booleans on independent shapes are
  thread-safe (OCCT's own `BOPAlgo` parallel mode and its documented
  per-thread allocator; `MMGT_OPT` env var) — if the `Solid` nodes run
  under the scheduler's chunked `each()` like every other node, the
  1,000-part figure divides by the core count, but that is an
  assumption to verify in WP-C, not a measurement.
- **Tessellation at 0.01 deflection: 0.85 ms per 32-triangle part**;
  OCCT's mesher dominates, the binding's extraction (one FFI call per
  node, UV, normal and triangle) is 1.5 % — fine as is, no need for a
  bulk copy seam in WP-B. The loft's B-spline faces (1,132 triangles)
  mesh in ~1 ms, so a display-cache miss on a `Solid` is ~1 ms per
  simple solid — inside the 0.5 ms p50 cheap-slider budget only via
  the hash-keyed tessellation cache (cache hit) — slider drags that
  re-run a boolean are ≥3 ms per solid regardless, i.e. B-rep
  pipelines will feel "compute-on-release" (Item 3b) sooner than mesh
  ones.

#### 4a. License row (draft for DECISIONS.md)

> **OCCT licensing.** OCCT 7.8.1 is `LGPL-2.1-only` **with the Open
> CASCADE Exception 1.0**: object code that incorporates material from
> OCCT header files (inline functions, templates, "CDL generic
> classes") may be distributed "under terms of your choice, provided
> that you give prominent notice in supporting documentation" that it
> uses OCCT. The exception covers exactly what our cxx glue and the
> `Handle<>`/`gp_*` inlines put into *our* object code; it does **not**
> relax LGPL §6 for the OCCT libraries themselves.
> *While private*: nothing is conveyed, nothing is triggered; the only
> obligation is hygiene (keep `LICENSE_LGPL_21.txt` +
> `OCCT_LGPL_EXCEPTION.txt` in the repo's third-party notices, record
> the exact build we link).
> *At go-public, shipping binaries*: **dynamic linking** (the conda
> `TK*.dll` / `libTK*.so` / `libTK*.dylib` beside the executable) is
> LGPL §6(b)'s "suitable shared library mechanism" — obligations are
> the notices, the prominent OCCT acknowledgement, and making the
> *corresponding source of the exact OCCT build* available (for
> conda-forge that is upstream `V7_8_1` + the feedstock's 16 patches at
> feedstock commit `4237a64ca19105111b57b8d18535e9de717d8870`, both
> public — pin that commit next to the package sha256s). **Static
> linking** (an own static prebuilt, or `builtin`) falls under §6(a):
> we would have to provide Cicada's own object files (or another
> relinkable form) so a user can relink against a modified OCCT —
> acceptable only if Cicada itself is open source at that point, and
> the reason static is not the v0.1 default.
> *The Rust binding is LGPL too*: `opencascade`, `opencascade-sys`
> (and the stray `kicad-parser`) are `LGPL-2.1` crates, and Rust links
> them **statically** — so the §6(a) analysis applies to the glue
> regardless of how OCCT itself is linked. If Cicada goes public as a
> proprietary binary, the seam must be Cicada-owned code (the surface
> Item 3 needs is ~25 functions: primitives, prism/loft/revolve/sweep,
> the three booleans, `BRepMesh_IncrementalMesh` + triangulation
> read-out, `BinTools` with explicit flags, STEP read/write) — the OCCT
> exception then covers our object code, and only the OCCT libraries
> stay LGPL. Decide the dependency shape (fork vs. own seam) with this
> in view; it does not block v0.1.

#### 4b. `deny.toml` rows (verified: cargo-deny 0.20.2 against the probe's lock file)

## Recommendation

**Go with prebuilt conda-forge shared OCCT 7.8.1 + bundling (DLLs /
dylibs / .so beside the executable), behind a `cicada-geom` `occt`
feature, the binding in an own fork that carries exactly the reviewed
patches in `tools/probes/occt-2026-08/patches/`** (0001 MSVC handle
aliases, 0002 BinTools symbol collision, 0003 Windows static system
libs; 0004 is for the source path only) plus the WP-B additions
(explicit-flag BinTools writer, `kicad-parser` dropped, `LGPL-2.1-only`
in the manifests). Evidence, in the order it was gathered:

1. **It works on MSVC today** with 25 mechanical source files of rename
   (Q1) — the only real upstream blocker — and nothing else: no build
   script edits, no link-lib additions, no cmake flags for the shared
   path. The detection (`DEP_OCCT_ROOT` → `find_package`) worked first
   try against the conda layout.
2. **It is cheap to build**: 28.5 s cold, 0.7 s relink, a 326 KB
   executable; the CI job is +3 min cold / +30 s warm per OS, with the
   kernel compile nobody has to wait for ever again.
3. **It is shippable**: 15 DLLs / 30 MB beside the exe for the
   modeling closure, proven to launch from a clean process; the 29+3
   DLL / ≈55 MB number applies only if the fork keeps the binding's
   whole link list — trimming it (or an `occt-step` sub-feature) is
   WP-A work.
4. **Determinism is not a reason to prefer any path**: byte identity
   across processes held for all four shapes in both formats and both
   tessellation buffers, AND across two different OCCT builds by two
   different MSVC versions (conda's `/O2` shared vs the unoptimized
   static source build). The remaining unknown — cross-OS libm /
   FMA — is identical for every option and is answered by the CI job.
5. **The source build is the worse deal on every axis measured**: 248–
   255 s here (≈15–25 min per OS on runners) per OCCT bump; it does
   not link on Windows without PR #216's libs; through cmake-rs it is
   silently unoptimized on MSVC (2–2.8× slower until the release flags
   are forced, patch 0004); static linking brings LGPL §6(a) at
   go-public. Its one genuine advantage — a single 31 MB self-contained
   executable, no loader-path story, no `MSVCP140` beyond what a Rust
   binary already implies — becomes interesting only if Cicada goes
   public as open source, at which point an own static prebuilt
   artifact (built with patch 0004's flags, fetched by the same
   `tools/fetch_occt.py`) is a contained follow-up, not a redesign.
6. **An own CI-built prebuilt (static or shared) buys nothing now**
   that conda-forge does not already provide for all four platforms at
   one build number from one feedstock commit — and it would need the
   same fetch script, the same feature gate, the same CI job, plus a
   second pipeline to maintain. Keep it as the documented fallback for
   the day conda-forge's 7.8.1 files disappear (they have not removed
   old builds historically; the URLs are version-addressed) or the day
   we need a patch set of our own in the kernel.

The `Solid` kind hashes its **canonical BinTools V4 bytes written with
`theWithTriangles = false, theWithNormals = false` and a pinned format
version**, after normalizing single-solid compounds — Q2 says that is
well defined and stable; the geometric-summary alternative is not
needed.

### The three biggest risks

1. **Licensing of the glue, not of OCCT.** The binding crates are
   LGPL-2.1 and Rust links them statically; if Cicada is ever
   distributed as a proprietary binary, §6(a) bites on the glue even
   though OCCT itself rides §6(b) as DLLs. Mitigation that costs least
   if decided early: treat the fork as a temporary scaffold and make
   the ~25-function seam Cicada-owned code (the OCCT exception covers
   our object code). This is a Ben decision, not a WP decision; it
   does not block v0.1 because nothing is conveyed while private.
2. **The upstream binding is thin where we need it thick.** One
   evening found two silent defects on the exact path `Solid` depends
   on (the BinTools writer that was secretly the text writer; the
   with-triangles default), an untested MSVC build (PR #230 closed
   unmerged, author's fork deleted), a `Compound`-wrapping `Cut`, an
   edge iterator that double-counts, and `kicad-parser` in the
   dependency tree. Expect every WP-C node to touch the glue and the
   fork to diverge quickly; budget review time for C++ changes
   (fail-loud rule: no `unique_ptr(nullptr)`-style silent failures in
   our additions — the existing `read_brep_bin` returns a null
   `UniquePtr` instead of an error type).
3. **Platform and runtime facts still unmeasured.** Linux/macOS
   build + load paths (conda's RPATH/install-name conventions for
   `libTK*.so`/`.dylib`, whether `DYLD_LIBRARY_PATH` survives SIP in
   CI, whether the Unix packages' modeling closure also avoids
   freetype) and cross-OS hash identity are all "expected fine,
   verified nowhere". Plus two smaller ones: conda-forge's OCCT is
   **not pristine** — 16 FreeCAD-ecosystem patches touch `BRepFill`
   (loft/pipe/sweep), `BRepOffset`, `ChFi3d` — so golden hashes pin
   that patched behaviour and a future conda rebuild can move them
   (mitigated by pinning the exact `_103` files); and `MSVCP140.dll`
   is a new runtime requirement on Windows machines without the VC++
   redistributable (mitigated by bundling it — it is redistributable).
