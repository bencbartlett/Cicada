### 00:20–00:55 — Q1: prebuilt build/link on Windows (MSVC)

**Binding.** `opencascade` / `opencascade-sys` from
`https://github.com/bschwind/opencascade-rs` at
`d114250a464d50cde1901743d3bf523a099d6887` (2026-08-03, HEAD of `main`
at probe time); crates.io carries only stale 0.2.0 releases. The probe
depends on it as `{ git, rev, default-features = false }` — the
`builtin` feature (source build of the OCCT 7.8.1 submodule via
`occt-sys`) is off, so `opencascade-sys/build.rs` runs its tiny cmake
project (`OCCT/CMakeLists.txt`: `find_package(OpenCASCADE REQUIRED)`,
writes `occ_info.txt`) with `register_dep("occt")`, which puts
`DEP_OCCT_ROOT` on `CMAKE_PREFIX_PATH`, then checks the version is 7.8.x.

**`DEP_OCCT_ROOT`** = `C:\Users\benja\AppData\Local\cicada-occt\occt-7.8.1-win64\Library`
(the dir holding `include/`, `lib/`, `bin/`, `lib/cmake/opencascade`).
Detection worked first try: cmake found `OpenCASCADEConfig.cmake`,
reported 7.8.1, `BUILD_SHARED_LIBS=ON` → the build script emits
`rustc-link-lib=dylib=TK…` for its 24 libs plus `user32`. Two harmless
cmake warnings (a `cmake_minimum_required(3.1)` deprecation; a syntax
warning in OCCT's own config file at `/wd"26812"`).

**First build: FAILED in the C++ glue (not in OCCT, not at link).**
`cargo build --release` → cc-rs compiling the 41 cxx bridge TUs, the
first failing TU (`b_rep.rs.cc`) with three `error C2440`. To get the
complete list at once I compiled all 41 TUs by hand with the same
flags (`compile_all.bat`, 19 s wall): **22 error sites in 10 TUs, one
root cause**, exactly the one PR #230 describes:

- On MSVC, OCCT's `Standard_Handle.hxx` (line 416 ff.) defines
  `Handle_X` via `DEFINE_STANDARD_HANDLECLASS` as a **class derived
  from** `opencascade::handle<X>` ("to allow exporting this type in
  C++/CLI"); on every other compiler it is a plain `typedef`. The
  binding declares its Rust-visible handle types under the names
  `Handle_X` and allocates `new opencascade::handle<X>(…)` into
  `std::unique_ptr<Handle_X>` — distinct types on MSVC.
- 17 allocation sites (`<function-style-cast>` C2440) in 7 headers:
  `b_rep.hxx` (3), `gc.hxx` (3), `geom.hxx` (5), `geom2d.hxx` (4),
  `geom_api.hxx` (1), `top_tools.hxx` (1) — plus `poly.hxx`, `law.hxx`,
  `t_col_gp.hxx` which already allocate `new Handle_X(ptr)` and compile.
- 5 signature mismatches in cxx-GENERATED code (`'initializing': cannot
  convert from 'overloaded-function'`): cxx assigns each bound function
  to a pointer of the exact declared signature, and `Handle_X` flows
  straight into OCCT APIs —
  `BRepLib_ToolTriangulatedShape::ComputeNormals(…, const Handle(Poly_Triangulation)&)`,
  `BRepOffsetAPI_MakePipeShell::SetLaw(…, const Handle(Law_Function)&, …)`,
  `ShapeAnalysis_FreeBounds::ConnectEdgesToWires(Handle(TopTools_HSequenceOfShape)&, …)`
  and the generic `handle_try_deref(const opencascade::handle<T>&)`
  (`poly.rs.cc`, `top_tools.rs.cc`). These five prove the cheap fix
  ("allocate `new Handle_X` instead") is insufficient: the C++ name the
  Rust side binds to must *be* `opencascade::handle<X>`.
- Nothing else fails: all other 31 TUs compile clean with `/W4`; the
  cmake detection, the include paths, and `/MD` vs the conda `/MD`
  libs all agree.

**Upstream PRs read as starting points.**
- **#230 "Fix MSVC handle name collisions"** (akalari, opened
  2026-08-19, **closed unmerged 2026-08-20 05:49 UTC, fork deleted, no
  discussion** — the `.diff` is still served by GitHub): 26 files,
  +147/−58. Mechanism: `bindings_common.hxx` forward-declares the 16
  wrapper-owned classes and adds `using RustHandle_X = opencascade::handle<X>;`
  for each; every glue header signature uses `RustHandle_X`; every
  Rust bridge `type Handle_X` gets `#[cxx_name = "RustHandle_X"]` (32
  attributes across 14 `.rs` files). Rust-side names are unchanged, so
  the high-level `opencascade` crate needs no edits. Plus a Windows CI
  job (`cargo check -p opencascade` with the bundled OCCT,
  `CMAKE_POLICY_VERSION_MINIMUM=3.5`).
- **#216 "Fix Windows build: CMake profile matching and missing system
  libraries"** (TonyMarkham, open since 2025-10-29): 2 files, +9/−1 —
  (a) `occt-sys` passes Cargo's `PROFILE` to cmake instead of hardcoding
  Release (a `builtin`-only problem: debug `cargo build` looked for
  `TKernel.pdb`); (b) links `advapi32`, `gdi32`, `shell32`, `comdlg32`
  on Windows. **Neither part applies to the prebuilt SHARED path**: the
  import libs resolve the Win32 symbols inside the DLLs (the probe
  linked with only the existing `user32`, no unresolved externals), and
  there is no cmake profile to match because we build nothing. Both
  parts WOULD apply to an own static prebuilt (PR #230's author hit the
  same `SetFileSecurityW`/`AddAce` unresolved externals in the bundled
  static build).

**Minimal patch needed and applied (every line recorded).** The
source-only part of #230 — its 25 source files, +131/−58, with the
workflow hunk dropped — is the minimum that compiles: the five
generated-code mismatches force the alias approach, and the alias
approach forces every header signature and every bridge type to
follow. I audited the diff line by line: besides `Handle_` →
`RustHandle_` renames it contains only the 16 forward declarations, the
16 `using` aliases, `#include <Standard_Handle.hxx>`, one
single-line → two-line reflow of `DynamicType` (clang-format), and
whitespace re-alignment of wrapped parameter lists. The exact diff is
committed as `tools/probes/occt-2026-08/patches/0001-msvc-handle-aliases.diff`
and was applied with `git apply` (clean) to a scratch clone at the
pinned rev (`C:\Users\benja\AppData\Local\cicada-occt\opencascade-rs-patched`
— the probe's download-cache dir rather than `%TEMP%`, so the
`[patch]` path in the committed `Cargo.toml` survives reboots). The
probe `Cargo.toml` carries
`[patch."https://github.com/bschwind/opencascade-rs"] opencascade = { path = … }`.
No other change to the binding was needed — no build.rs edit, no

**Shared vs static; DLL count; PATH.** The conda package is
**shared-only** (`BUILD_SHARED_LIBS ON`; the `.lib`s are import libs).
`dumpbin /dependents` on the probe exe and transitively on the DLLs:

- The linker kept only the **8** TK import libs actually referenced
  (`TKernel TKMath TKBRep TKTopAlgo TKPrim TKMesh TKBO TKOffset`) of the
  24 the build script lists; transitively the process needs **15 OCCT
  DLLs, 30.0 MB**: `TKBO TKBRep TKBool TKFillet TKG2d TKG3d TKGeomAlgo
  TKGeomBase TKMath TKMesh TKOffset TKPrim TKShHealing TKTopAlgo TKernel`.
  Non-OCCT imports: `KERNEL32 ADVAPI32 USER32 WSOCK32`, the UCRT
  api-sets (in the OS since Windows 10), and `MSVCP140 VCRUNTIME140
  VCRUNTIME140_1` — the VC++ 2015–2022 redistributable. A Rust MSVC
  binary already depends on `VCRUNTIME140` + UCRT; `MSVCP140.dll` (the
  C++ standard library) is the one genuinely new runtime requirement.
  **No `freetype.dll` / `FreeImage.dll`** for this set.
- If the shipped build links the binding's whole list (Item 3 WP-C adds
  STEP in/out → `TKDESTEP TKXSBase TKDE TKXCAF TKCAF TKLCAF …`), the
  closure grows to **29 TK DLLs, 49.0 MB**, and via
  `TKCAF → TKV3d → TKService` drags in `freetype.dll`, `FreeImage.dll`
  and `WINMM.dll` — two more conda packages to fetch and ship
  (`freetype`, `freeimage`, each with their own LGPL/FreeImage-license
  rows). A fork that links only what it binds (or a `cicada-geom`
  feature split `occt-step`) keeps the 15-DLL closure for everything
  but STEP; whether STEP alone can avoid `TKCAF` is a WP-A question
  (`STEPControl_Reader/Writer` live in `TKDESTEP`, which itself imports
  only `TKXSBase TKShHealing …` — the CAF libs come from the binding
  linking `TKCAF/TKLCAF/TKXCAF` for XCAF colours/names).
- **PATH at runtime: yes, required.** Launching the exe with a clean
  environment (`Process.Start`, cwd elsewhere) exits with
  `0xC0000135 STATUS_DLL_NOT_FOUND`; the msys shell reports it
  confusingly as `api-ms-win-crt-locale-l1-1-0.dll: cannot open shared
  object file`. It runs with `Library\bin` on `PATH`, **or with the 15
  DLLs copied next to the exe** (verified: `bundle-test/` = exe + 15
  DLLs = 29 MB on disk, launched from another working directory → exit
  0, `smoke OK`). A shipped `cicada.exe` would therefore carry ~15 DLLs
  (30 MB) beside it, or ~29 + 3 (≈55 MB) with STEP through the
  binding's current link list. (A false-PASS trap worth recording: my
  first "runs without PATH" observation was because the shell's cwd was
  `Library\bin` — Windows searches the cwd; don't test DLL resolution
  from inside the DLL directory.)

**Q1 verdict: GREEN with one patch.** The prebuilt-shared path works on
MSVC today with the reviewed, mechanical PR-#230 rename carried in an
own fork (its upstream PR was closed without merge, so "wait for
upstream" is not a plan). Linux/macOS are expected to be strictly
easier (the `Handle_X` typedef path; CI-verified in upstream's Linux
job for the builtin build) but are NOT verified by this probe — that is
the CI job of Item 3 WP-A.
